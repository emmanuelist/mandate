## Traps
- **Zest takes funds from `contract-caller`.** Both `deposit` (line 765) and `redeem` (line 799) of `v0-vault-sbtc` bind `account` to `contract-caller`. A contract placed between the vault and Zest is Zest's account for that call: it pays, and it holds the funds for an instant (#5, #6). Deployed source, 2026-10-13.
- **Zest fills exactly at its quote within a call:** `deposit` returns what `convert-to-shares` quoted and `redeem` what `convert-to-assets` quoted, so a zero-slippage mandate works on Zest. A 100,000-sat round trip returns 99,999: share rounding, not a fee. E-011.
- **Zest's smallest deposit.** 1 sat rounds to zero shares and fails with `(err u801010)`; 10 sats works. `tests/minimum.test.ts`, 2026-10-13.
- **Bitflow's guard sits one contract below the core.** The core contracts have no `is-standard` check on trader paths; the pools do (E-003). Reading the core alone suggests contracts are fine.
- **Granite's lending pool lends USDCx.** Posting sBTC to Granite is collateral for borrowing, a different action from lending, and `borrower-v1 remove-collateral` needs a signed Pyth price update (`(buff 8192)`), so it can't sit behind the venue trait. State-v1 balances, September 2026; borrower-v1 source, 2026-10-14.
- **Granite accrues interest when a call starts**, so a deposit mints slightly fewer LP tokens than a quote taken just before: 99,799,935 against a quote of 99,801,116 for 100 USDCx. A 100 USDCx round trip returns 99.999999. E-028.
- **Jing fills need a signed Pyth update**, so they can't be tested on a fork. On 2026-10-07 v6-2 had six transactions in total, and v5 and v6 were paused.
- **Testnet has an official sBTC among more than a dozen look-alikes:** `SN3VMHXEN64ZZF71JQ5VESXDWTR301XTTXGF4J8F1.sbtc-token`. The network table at docs.stacks.co ("Mainnet and Testnets") names it, its deployer also deployed `sbtc-registry`, `sbtc-deposit` and `sbtc-withdrawal`, it has `protocol-mint` and the seven SIP-010 functions, and it was deployed at block 1,162 on 2026-08-06, the day after the reset. On 2026-10-14 it had 98 holders. The Hiro Platform faucet (platform.hiro.so/faucet) hands out testnet sBTC 10,000 sats at a time, sent from `STDMN71Z0H9EF8CRKAWTGBB5YS0BNV26HZ79QFFP`: account 1's 230,000 sats arrived that way, and the owner confirmed the source on 2026-10-14. An earlier entry here said none of the testnet tokens was official; that was wrong. Contract API, 2026-10-14.
- **Testnet has no Zest:** Zest's v2 repository has only local simnet setups, with no testnet deployment found. Repository tree, 2026-10-13.
- **Testnet has no standard SIP-010 trait.** The reset erased it: `sip-010-trait-ft-standard` under `ST3FBR2AGK5H9QBDH3EEN6DF8EK8JY7RX8NQXMNRQ` (mainnet's deployer, on testnet) and under `ST1NXBK3K5YYMD6FD41MVNP3JS1GABZ8TRVX023PT` both answer 404, so a contract that names it can't deploy there. The vault carries its own copy (D-014). `/v2/contracts/interface`, 2026-10-14.
- **A testnet contract can't be redeployed under the same name.** `npm run testnet` skips a contract that's already deployed only if its source is identical to the repo's, and otherwise stops before sending anything. A changed contract needs a fresh testnet account (a new seed in `settings/Testnet.toml`). Tested by editing a contract locally, 2026-10-14.
- **Two SIP-010 traits.** Bitflow defines its own (`SM1793C4R5PZ4NS4VQ4WMP7SKKYVH8JZEWSZ9HCCR.sip-010-trait-ft-standard-v-1-1`); Granite and Jing use the canonical one (`SP3FBR2AGK5H9QBDH3EEN6DF8EK8JY7RX8QJ5SVTE.sip-010-trait-ft-standard`). One trait type can't cover every venue. `contracts/granite-probe.clar`.
- **A venue must name the token it moves.** The venue trait's `deposit (amount min-out recipient)` takes no token, so a venue calls its token by a fixed principal. A venue that names a testnet contract can't deploy on a mainnet fork, where that contract doesn't exist, so `mock-venue-sbtc` is tested on a testnet fork instead (D-017).
- **Trait conformance is structural.** A contract can be passed as a trait it never declares if its functions match: Zest's vault as Mandate's venue trait (E-009), and sBTC as Bitflow's SIP-010 trait in v2's tests.
- **An `as-contract?` allowance on the venue's own token covers the venue burning the vault's shares on redeem** (`with-ft <venue> "*" <shares>`). E-009.
- **Only four devnet accounts exist:** `deployer` and `wallet_1` to `wallet_3` (`settings/Devnet.toml`). Tests that need a stranger reuse `wallet_2`.
- **An exceeded `as-contract?` allowance fails the call with `(err u<n>)`**, where n is the violated allowance's position in the list, so the vault's single allowance gives `(err u0)`. E-012.
- **Clarity blocks a call back only into the function already running.** A venue the vault calls can call back into any other public function of the vault mid-call, as itself: `contract-caller` is the venue. A call back into the running function aborts the whole transaction with `RuntimeCheck(CircularReference(["<contract>:<function>"]))`, and the SDK throws a string rather than returning a result. A call back that acts on the venue's own books succeeds, which is how v4 credited a venue's deposit twice during an unwind (#48, E-035). Under v3's `tx-sender` rule the call back ran as the vault instead (E-012). v5 refuses every write while a venue runs (D-022).
- **A public function satisfies a trait's function signature**, so a venue's `get-balance` and quotes can run code and call out, not only its `deposit` and `redeem`. `contracts/reentrant-venue.clar` declares all five as public, and the vault calls it through the venue trait (E-035).
- **`as-contract?` returns `(err u128)` when an asset it has no allowance for leaves the contract** during its body; an exceeded allowance in the list returns that allowance's index instead (Clarity's function reference, `as-contract?` and `restrict-assets?`). Seen when a venue withdrew from v4 while v4's redeem, which allows only the venue's share token, was running (E-035).
- **`tx-sender` passes through every contract a user calls.** A contract an owner calls runs with the owner as `tx-sender`, so authorizing by `tx-sender` lets it act as the owner. v3 was open to this (E-027); v4 authorizes by `contract-caller` (D-019).
- **Burns count as sends for post-conditions.** In deny mode a burn of a principal's tokens needs a post-condition, just as a transfer does; mints need none. The reference delegate's unwinds carry `vault sent_equal_to <shares>` of the venue's share token, and pass. Testnet, 2026-10-14 (E-031).
- **Clarinet SDK 3.23.2 doesn't evaluate post-conditions**, so they can only be checked on a real network; 3.24.0's release notes add post-conditions in simnet. 2026-10-14.
- **`try!` needs a known error type.** A function that only ever returns `(ok ...)`, such as v4's `allow-asset`, has an indeterminate error type, so `try!` on a call to it fails type-checking; use `unwrap-panic`. v5's can return `u120`, so `try!` works. `contracts/reentrant-venue-v4.clar`, 2026-10-14.
- **`check_checker` with `callee_filter = true` is nondeterministic.** On v5 it reported 14 warnings in 6 of 10 runs and 19 in 4; with it off, 26 in 10 of 10. `Clarinet-review.toml` keeps it off (E-036).
- **`clarinet check` can't resolve `Clarinet-jing.toml`.** Jing's market contract names `SPMV5HDZ4EMB8XY7HAYT3XW0DF7DZ4E8XEG2J1T8.pyth-lazer-decoder-v1`, which isn't a listed requirement, so the check errors with `use of unresolved contract`; the SDK resolves it on the fork, and the Jing suite passes. 2026-10-14.
- **A faucet payout can land in the middle of a run.** The Hiro Platform faucet's address, `STDMN71Z0H9EF8CRKAWTGBB5YS0BNV26HZ79QFFP`, sent the owner 10,000 sats of testnet sBTC at block 725,677, between two steps of the lifecycle run, and broke its reconciliation of the owner's wallet. `/extended/v1/address/<address>/transactions_with_transfers` lists each transaction's `ft_transfers` (sender, recipient, amount, asset), and the run now reconciles net of transfers outside its own transactions (E-037).
- **A refused call is still mined.** A contract call whose function returns `err` costs its fee and confirms with `tx_status` `abort_by_response`, its `tx_result` the error, and `event_count` 0. Signed in deny mode with no post-conditions, it couldn't move an asset even if accepted (D-024, E-037).
- **All manifests share one simnet plan file**, `deployments/default.simnet-plan.yaml`. A run whose manifest's plan differs from the file rewrites it as workers start, and a worker can fail to start reading it half-written: seen once, on the first local-suite run after `Clarinet-local.toml` was created, and the next six runs passed. CI retries every suite (D-015). 2026-10-14.
- **The suites that touch only local contracts need no fork.** On `Clarinet-local.toml`, which has no `[repl.remote_data]`, they ran 93 tests in 5 files in about 3 s and sent nothing to Hiro (#45); after #48, 119 tests in 7 files in about 11 s. 2026-10-14.
- **A contract that doesn't type-check stops the simulator from starting**, and vitest reports only `Failed to start forks worker`, the same message a rate-limited fork gives. After a contract change, run `clarinet check` before blaming the network. 2026-10-14.
- **`as-contract?`'s body can't end in a response.** Put `try!` inside the body. `contracts/c4probe.clar`.
- **Forking at the tip crashes the SDK now and then.** The SDK reads the tip height, then asks Hiro for that block; a lagging API node answers 404 "Block not found", and the SDK panics instead of retrying (`remote_data/mod.rs:281`, a `Result::unwrap()`), killing the worker. Seen in CI on 2026-10-13. The forks are pinned to settled blocks instead (D-012).
- **Upgrading the SDK doesn't change forking:** between 3.23.2 and 3.24.1, 36 commits changed 175 files and none of the forking code. In 3.24.1, `remote_data/mod.rs` still unwraps `/v2/info` (line 237) and the block fetch (line 281); rate limits (429) are retried in the HTTP helper, any other error still panics. `gh api repos/stx-labs/clarinet/compare/v3.23.2...v3.24.1` and the file at v3.24.1, 2026-10-14.
- **The SDK also panics when a fetch fails outright**, pinned block or not: `remote_data/mod.rs:237`, `Result::unwrap()` on "fetch failed". It cost one file in the first attempt of #20's CI run ([38485977559](https://github.com/emmanuelist/mandate/actions/runs/38485977559)); the second attempt passed (D-013).
- **Many workers at once: some fail to start.** With Vitest's default worker count, 3 of 17 files failed to start at the pinned block (local, 2026-10-13); each passed alone, and the full suite passed with two workers (E-013). The cause is inferred, not proven: every worker boots its own fork from Hiro at the same moment.
- **Vitest 4 ignores `poolOptions`**, so `singleFork` never took effect; the worker count is the top-level `maxWorkers`.
- **The SDK caches fork data in `.cache/datastore`**, one entry per contract, key and block. With that cache restored in CI, #17 failed the same two tests twice, with runtime type errors inside Zest's (`v0-vault-sbtc:482`) and Bitflow's (`xyk-core-v-1-2:566`) forked contracts. Without it, #19 still failed, two workers not starting right after a burst of rate-limit waits. CI no longer caches it, and retries the fork suites instead (D-013).
- **A fork worker started inside Hiro's rate-limit window can fail to start at once**, printing only `[vitest-pool]: Failed to start forks worker` and no panic. On `main` after #21 the Jing suite failed three times in 2.6 s, starting 3 s after Hiro had told the runner to wait 29 and 53 s. In the rerun it also started inside a window but its worker came up, and the SDK waited out the rate limit (E-020). Hiro's waits in our logs run from 1 to 57 s, so a CI retry waits 60 s (D-015).
- **npm 11 skips install scripts it has not been told to allow**, and warns about `fsevents@2.3.3`, an optional macOS file-watching dependency. `vitest run` does not use it, and CI's Linux runners do not install it. Fresh clone, 2026-10-14 (E-022).
- **Rate-limit waits are routine:** CI runs on 2026-10-13 hit Hiro's limit 11 to 13 times each, local runs 1 to 11. Only CI has failed with two workers. The SDK has no setting for an API key. Moving the five local-only files off the fork (#45) did not lower the fork suite's own waits: 11 to 14 per CI run on 2026-10-14, most of them 48 to 57 s (E-034).
- **Fork tests run at pinned blocks:** the main suite at 9,194,000 (2026-10-13 06:41 UTC) and the Jing suite at 9,036,500. A mainnet change after those blocks doesn't show until the height is bumped on purpose (D-012).
- **Hiro rate limits.** The SDK waits 40 to 55 s and retries when rate-limited. On 2026-10-13 a local full run was limited 11 times and passed in 117 s; on GitHub's runners, 11 times and 249 s (E-008). No API key is needed for the suite to pass.
